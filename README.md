# tg_drop_bot

Telegram-бот для розыгрышей в каналах: админка, капча для участников,
PostgreSQL, Docker-деплой и публикация релизных образов через GitHub Actions.

## Возможности

- Админка в личке бота для пользователей из `ADMIN_IDS`.
- Создание розыгрыша пошаговым мастером: канал, название, описание, условия, картинка,
  количество победителей, дедлайн.
- Автоматический список каналов, где бот добавлен администратором.
- Участие через кнопку под постом и deep link в личку бота.
- Капча с изображением на каждый розыгрыш через пакет `captcha`.
- Мягкий Redis rate limit/debounce от спама сообщениями и кнопкой участия.
- Проверка подписки на канал при участии и перед выбором победителей.
- Счетчик участников в посте канала с фоновым обновлением по расписанию.
- Выгрузка списка участников в табличный `.csv` файл.
- Автоматическое завершение по дедлайну и ручное досрочное завершение.
- Docker-first локальный и продакшен-запуск.

Решённые капчи удаляются сразу при обработке ответа, одновременно с сохранением
участника. Факт прохождения хранится в поле `captcha_passed_at` участника.
Обновление картинки удаляет предыдущую капчу. Планировщик каждые
`SCHEDULER_INTERVAL_SECONDS` удаляет до 1000 просроченных капч, записей с истёкшей
паузой после неудачных попыток и капч закрытых розыгрышей. Действующие капчи
и паузы для открытых розыгрышей сохраняются.

## Защита от повторных заходов

Для новых розыгрышей бот сохраняет события вступления и выхода из каналов.
У подтверждённо подписавшихся после публикации вес при выборе победителей 0,7,
у остальных 1. Неизвестная дата подписки не считается доказательством нового
вступления. Старые опубликованные розыгрыши сохраняют равные шансы.

Правильный ответ на капчу быстрее двух секунд уменьшает вес заявки вдвое:
с 1 до 0,5 или с 0,7 до 0,35. Участие по-прежнему засчитывается. Сохраняется
только время ответа в миллисекундах; старые заявки без замера не меняются.

Отписки сохраняются в истории и не создают автоматических запретов.
Администратор может запретить участие по Telegram ID или `@имени` через меню
«Исключения» для конкретного канала. По имени бот ищет среди известных ему
заявок и сверяет владельца с Telegram. Если имя не найдено или не подтверждено,
нужно ввести числовой ID. Сам запрет привязан к ID и не пропадает при смене имени.
Бот отклоняет новые заявки до капчи и не допускает
запрещённых участников к выбору победителей. Повторная подписка не снимает
запрет; его можно снять в том же меню.

Численные коэффициенты и список запретов доступны организаторам. Пользователь
с запретом получает отказ с указанием на бота обратной связи в описании канала.
В карточке розыгрыша есть кнопка «Защита розыгрыша», в выгрузке участников
отражаются вес и основание допуска. История подписок до включения наблюдения
не восстанавливается: для завершённых до обновления розыгрышей собирается только
доступная история без автоматических исключений за неизвестный стаж.

Боту необходимы права администратора и обновления `chat_member`.
Подписка перепроверяется при выборе победителей. События подписок хранятся год;
сведения, необходимые для допуска и объяснения исключений, сохраняются отдельно.
Внизу активного поста бот сообщает об автоматическом выборе и антифрод-проверках.
После завершения вместо этого абзаца показывается «Участие закрыто.».
Отдельное сообщение с итогами не повторяет абзац об антифроде.

## Запуск сохраненного черновика

Откройте «Черновики», выберите розыгрыш и нажмите «Перейти к запуску».
Бот покажет актуальный предпросмотр поста и канал публикации. Если не все поля
заполнены, меню подскажет, что нужно настроить; кнопка «Вернуться к настройкам»
откроет карточку розыгрыша. Кнопка «Опубликовать и запустить» отправляет пост в
канал и открывает участие. Сам переход к предпросмотру ничего не публикует.

Для поста с картинкой бот проверяет лимит подписи при добавлении картинки и
изменении текста. В лимит входят название, описание, служебный текст и запас
для роста счётчика участников. Если подпись не помещается, сократите описание
или продолжите без картинки.

## Локальная разработка

Требуется Docker и `uv`.

```powershell
uv venv --python 3.12
uv sync --dev
Copy-Item .env.example .env
docker compose up -d postgres
docker compose up -d redis
uv run alembic upgrade head
uv run python -m tg_drop_bot
```

Для локального теста используйте `TELEGRAM_MODE=polling`.

Бота нужно добавить администратором в тестовый канал. После этого канал появится
в меню админки. Если канал не появился автоматически, откройте в админке пункт
`Каналы` и нажмите `Выбрать канал`.

## Переменные окружения

Создайте `.env` из `.env.example` и заполните:

- `BOT_TOKEN` - токен от BotFather.
- `ADMIN_IDS` - Telegram user ID админов через запятую.
- `DATABASE_URL` - async SQLAlchemy URL PostgreSQL.
- `REDIS_URL` - Redis URL для мягкого rate limit/debounce.
- `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` - настройки PostgreSQL
  для Docker Compose.
- `APP_SECRET_KEY` - длинная случайная строка для хеширования CAPTCHA.
- `TELEGRAM_MODE` - `polling` локально, `webhook` на продакшене.
- `WEBHOOK_URL`, `WEBHOOK_PATH`, `WEBHOOK_SECRET` - настройки webhook.
  В продакшене `WEBHOOK_URL` также используется Caddy для выпуска TLS-сертификата.
- `CAPTCHA_LENGTH`, `CAPTCHA_TTL_SECONDS`, `CAPTCHA_MAX_ATTEMPTS`,
  `CAPTCHA_COOLDOWN_SECONDS` - длина кода, срок жизни, количество попыток и пауза
  после проваленной капчи.
- `SCHEDULER_INTERVAL_SECONDS` - интервал фонового завершения розыгрышей и обновления
  счетчика участников в постах.
- `RATE_LIMIT_ENABLED`, `RATE_LIMIT_USER_UPDATES`, `RATE_LIMIT_USER_WINDOW_SECONDS`,
  `RATE_LIMIT_PARTICIPATE_SECONDS` - мягкие лимиты от спама и повторных нажатий.

Rate limit не жесткий: по умолчанию допускает несколько апдейтов за короткое
окно и отдельно дебаунсит кнопку участия. Если Redis временно недоступен, бот не
падает и пропускает апдейты без ограничения.

Даты в админке вводятся в формате `ДД.ММ.ГГГГ ЧЧ:ММ`; таймзона задается через
`APP_TIMEZONE`, по умолчанию `Europe/Moscow`.

## Продакшен-деплой

Compose для продакшена использует готовый образ и сам поднимает Caddy для HTTPS.
На новом сервере достаточно положить файлы проекта, создать `.env` и запустить
compose:

```bash
cp .env.example .env
# заполните BOT_TOKEN, ADMIN_IDS, APP_SECRET_KEY, POSTGRES_PASSWORD и webhook-поля
docker compose -f docker-compose.prod.yml pull
docker compose -f docker-compose.prod.yml up -d
```

Минимальные значения для продакшена:

```dotenv
BOT_TOKEN=123456:replace-me
ADMIN_IDS=123456789
POSTGRES_PASSWORD=replace-with-long-random-password
APP_ENV=production
APP_SECRET_KEY=replace-with-long-random-secret
TELEGRAM_MODE=webhook
WEBHOOK_URL=https://bot.example.com
WEBHOOK_PATH=/telegram/webhook
WEBHOOK_SECRET=replace-with-long-random-secret
```

Caddy публикует порты `80` и `443`, автоматически получает сертификат Let's
Encrypt и проксирует Telegram webhook во внутренний контейнер бота. Порт бота
наружу не публикуется.

По умолчанию используется `ghcr.io/soaqa/tg_drop_bot:stable`. Для rollback
закрепите конкретный тег:

```bash
IMAGE_TAG=v0.6.1 docker compose -f docker-compose.prod.yml up -d
```

Watchtower включен в `docker-compose.prod.yml`, но работает только с контейнерами,
у которых есть label `com.centurylinklabs.watchtower.enable=true`. PostgreSQL он
не обновляет.

### Очередь участия

Очередь включается в режиме webhook через `PARTICIPATION_QUEUE_ENABLED=true`.
Включайте её между розыгрышами: уже выданные старым способом капчи не
переносятся в очередь. Укажите приватный `APP_SECRET_KEY`, не меняйте его
пока есть выданные капчи. Укажите `IMAGE_TAG=v0.14.0` в `.env`, чтобы
обновлять оба контейнера вместе:

```bash
docker compose -f docker-compose.prod.yml --profile participation-queue up -d
```

По умолчанию принимается 50 новых заявок в секунду с запасом на всплеск до 100.
При перегрузе ограничиваются новые заявки, не ответы на выданные капчи.
Предупреждения обрабатываются отдельно и не могут вытеснить заявки или капчи.
При затяжном наплыве не все предупреждения удастся доставить.
Принятые задачи записываются в PostgreSQL; Redis и Dramatiq доставляют воркеру
их идентификаторы. Потерянное сообщение брокера будет поставлено в очередь
повторно. Бот не разыгрывает призы, пока есть принятые заявки на проверке
или ещё действует выданная капча. После пяти минут ожидания организатор
получит предупреждение. Ручное завершение тоже дожидается принятых заявок.

Для нагрузочного теста на локальных PostgreSQL и Redis задайте
`TEST_DATABASE_URL`, `TEST_QUEUE_REDIS_URL` (отдельная тестовая база Redis)
и `RUN_QUEUE_LOAD_TEST=1`, затем запустите
`uv run pytest -s tests/test_participation_queue.py`. Запросы в Telegram
заменены локальным тестовым API.

## GitHub Actions и GHCR

`CI` запускается на push и pull request в `main`:

- поднимает PostgreSQL как GitHub Actions service container;
- устанавливает зависимости через `uv`;
- запускает `ruff`, `mypy`, миграции Alembic и `pytest`;
- собирает Docker image без публикации.

`Release` запускается на git tags `v*`:

- повторяет проверки;
- собирает Docker image;
- публикует теги `vX.Y.Z` и `stable` в GitHub Container Registry:
  `ghcr.io/soaqa/tg_drop_bot`.

Чтобы package был связан с репозиторием, workflow добавляет OCI label
`org.opencontainers.image.source=https://github.com/SoaQa/tg_drop_bot`.

Если репозиторий публичный, GHCR package можно сделать публичным в GitHub UI:
`Packages -> tg_drop_bot -> Package settings -> Change visibility`.
